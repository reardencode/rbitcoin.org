Architecture

Design uniqueness in plain language. Normative layouts live in the node repo; this page is the newcomer map.

One-screen picture

Peers feed IBD densify; confirm is lookup → load → scripts → write with a sole Class A appender.

Peers (BIP324 v2) │ ▼ IBD densify getdata ──► in-RAM body queue │ │ │ ▼ │ Confirm: lookup → load → scripts → write │ (sole Class A appender + Class C tip) │ │ └──── Mempool / tip follow ────┘ │ Reconstruct wire ◄────┤ Electrum joins ◄────┘ Class A + SH + mempool

Storage center is a transaction-relational archive on map-free tables (pread/pwrite + fallocate; no process mmap of Class A/B/C)—not a UTXO set + LevelDB chainstate.

vs Bitcoin Core

Different goals: smaller full archive, Electrum in-process—not every Core product surface.

Concern rbitcoin Bitcoin Core (typical)
Primary store Map-free Class A/B/C tables; page cache as L0 blocks/blk*.dat + undo + LevelDB chainstate (UTXO)
Historical blocks Reconstruct from packed tx archive; tip wire ring Serve raw blk / undo
Spentness Annotations on creates; no mutable UTXO set as truth Coins view / UTXO mutations
Script verification Pure Rust in-tree (secp256k1 via rust-bitcoin) libbitcoinconsensus / C++ interpreter
Electrum In-process index on confirm External (Fulcrum, ElectrumX, …)
Transport BIP324 v2 only v1 + v2
Scope Full node + Electrum backend; no wallet/mining/GUI/prune Full Core product surface

vs external Electrum indexers

Same process as the validating node; Class A is authoritative.

Concern rbitcoin Typical external indexer
Data source Validating node + archive in one process Reads Core RPC or blk files after the fact
Scripthash index Written on confirm (bulk at tip) Separate DB built by scanning history
Unconfirmed Mempool attached in-process Depends on Core mempool RPC
Consensus This binary validates blocks/scripts Trusts the node it indexes

Class A / B / C (intuition)

A — canonical archive: headers, packed txs (append + HWM publish). B — forever-open indexes (e.g. Electrum scripthash). C — tip / confirmation; tip advance is the commit.

Spents are annotations—not rewriting old outputs as a UTXO bag. Segmented tx.head makes newer txs resolve hottest.

Concurrent IBD / IO

Fixed writer roles (one Class A appender), allocate-then-publish HWMs, confirm split so disk work, script verify, and publish can overlap. Bulk io_uring where available; pread/pwrite fallback. Linux-shaped IO.

No multi‑GiB dbcache flush pauses: confirm is lookup → load → scripts → write.

Full archival only. There is no pruning option. An aspirational goal is ~1 day IBD on a modern laptop; that may require substantial RAM with this architecture and is a goal, not a shipped SLA. Truly “low cost” full nodes still face the random-access working set of possibly-spendable outputs—proof accumulators (e.g. utreexo-class) are a different design path.
